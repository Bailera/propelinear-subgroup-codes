# Propelinear Subgroup Codes

Code, data and verification scripts accompanying the paper

> *Propelinear Subgroup Codes: A Generalization of Subspace Codes with Improved
> Bounds*, I. Bailera, D. Crnković, A. Švob.

A **propelinear subgroup code** with parameters $(n,d,k)$ is a family of
nondegenerate subgroups of order $2^k$ of the group

$$U_n=\mathbb{F}_2^n\rtimes S_n,\qquad (x,\pi_x)(y,\pi_y)=(x+\pi_x(y), \pi_x\pi_y),$$

pairwise at propelinear distance at least $d$, where

$$d_P(C_i,C_j)=2k-2\log_2\lvert C_i\cap C_j\rvert .$$

The intersection of two subgroups is a subgroup, so its order is a power of
two and $d_P$ takes only even values; requiring $d_P\ge d$ is equivalent to
$\lvert C_i\cap C_j\rvert\le 2^{(2k-d)/2}$, which is the threshold the
verification script checks.

Here the action is $(\pi(v))_i=v_{\pi^{-1}(i)}$ and the composition is
$(\pi\sigma)(i)=\pi(\sigma(i))$; a subgroup is *nondegenerate* when its vector
parts are pairwise distinct, i.e. $\lvert\mathrm{supp}(C)\rvert=\lvert C\rvert$.

File names encode the parameters as digits: `clique_663.json` is $(6,6,3)$ and
`clique_10105.json` is $(10,10,5)$. Each file is a JSON list of codewords; each
codeword is a list of its $2^k$ elements, and each element is a pair
`[vector, permutation]` with the vector in $\mathbb{F}_2^n$ and the permutation
a tuple `p` in one-line notation, `p[i]` being the image of `i` (zero-based).

## Verifying the results

The verification script is deliberately independent of the generation code: it
recomputes the group operation from its definition, checks that the operation
is associative, and then tests every codeword and every pair from first
principles, so that an error in the search code cannot produce a false
positive.

```
python code/verify_psc.py cliques/clique_663.json
python code/verify_psc.py cliques/*.json
```

For each file it checks that

1. every codeword has order $2^k$;
2. every codeword is nondegenerate;
3. every codeword is closed under the twisted product;
4. no pair shares more than $2^{(2k-d)/2}-1$ nonidentity elements, which is
equivalent to $d_P\ge d$.

The threshold in (4) is **not** always zero. For $d=2k$ distinct codewords may
meet only in the identity, but for $d<2k$ sharing one nonidentity element is
permitted, and the script computes the correct bound from $(n,d,k)$. The exit
status is 0 if all checks pass, so the script can be used in a test suite.

Parameters are inferred from the leading digits of the file name whenever that
is unambiguous -- `clique_663.json`, `clique_10105.json`,
`clique_202010_lift.json` and `spreadcompat_884.json` all resolve correctly --
and can always be given explicitly with `--n --d --k`:

```
python code/verify_psc.py cliques/spreadcompat_884.json --n 8 --d 8 --k 4
```

## Reproducing the results

Exact values for $k=2$ follow from exhaustive enumeration: every subgroup of
order $4$ is either cyclic or elementary abelian, hence generated by one
element of order $4$ or by two commuting involutions.

```
python code/exact_k2.py --n 5 --d 4 --aq 9
python code/exact_k2.py --n 6 --d 4 --aq 21
python code/exact_k2.py --n 7 --d 4 --aq 41
```

For $k\ge 3$ no exhaustive enumeration is available. Candidate pools are
sampled with `psc_gen.py` and a clique is then extracted by a greedy pass
followed by an ILP restricted to a subpool around the incumbent:

```
python code/ilp_subpool.py --pool pool.pkl --n 6 --d 6 --k 3 --aq 9 \
    --seed cliques/clique_663.json --max-subpool 20000 --time-limit 3600
```

The ILP never returns a clique smaller than its seed, so repeated runs with a
growing subpool improve the bound monotonically. Both scripts write a companion
`results_<ndk>.json`, with slightly different schemas: `exact_k2.py` records
`status` and a boolean `exact`, since only a CBC status of `Optimal` certifies
an exact value, while `ilp_subpool.py` records the solver status inside
`method` together with the pool and subpool sizes, its optimum being optimal
over the subpool rather than over the pool.

Candidate generation draws on five complementary generators -- the algorithmic
form of the three conceptual sources described in the paper -- because no single
one covers the search space: linear codewords built explicitly from subspaces in
reduced row echelon form (these never arise from sampling, as they require the
identity permutation at every support vector); a walk up the subgroup lattice;
a walk restricted to commuting involutions, which is the only practical route
to the elementary abelian codewords $\mathbb{Z}_2^k$; a mixed-order walk
covering the intermediate values of the minimal number of generators; and a
structured construction. Permutations of $2$-power order are constructed rather
than sampled: involutions alone, for instance, make up only $0.26\%$ of
$S_{10}$, so rejection sampling finds essentially nothing.

At $d=2$ every pair of distinct $k$-subspaces already has $d_S\ge 2$, so
$A_2(4,2,k)$ is the total number of $k$-subspaces of $\mathbb{F}_2^4$, namely
the Gaussian binomial $\binom{4}{k}_2$: $1,15,35,15,1$. The propelinear column
behaves the same way: at $d=2$ the threshold $\lvert C_i\cap C_j\rvert\le
2^{k-1}$ is so weak that no pair of distinct nondegenerate subgroups violates
it, so $A^P_{nd}(4,2,k)$ is simply the number of nondegenerate subgroups of
order $2^k$ -- the four values $66$, $252$, $276$, $88$ quoted above. At $d=4$ only $k=2$
admits more than one codeword, and there a spread of five lines exists; for
$k=1,3,4$ the distance $4$ is unattainable, and likewise for every $d\ge 5$.

`clique_442.json` realizes $A^P_{nd}(4,4,2)=24$ and is shared between this
table and the main theorem, since $(4,4,2)$ is the $k\mid n$ base case of both.

### Product construction

A codeword is *spread-compatible* when its permutation is nontrivial at every
nonzero support vector. Given $m$ pairwise disjoint spread-compatible codewords
of order $2^k$ in $U_n$ with $k \mid n$, the product construction gives
$A^P_{nd}(2n,4k,2k) \ge (2^{2n}-1)/(2^{2k}-1) + m$.

|lift|$m$|$A^P_{nd} \ge$|$A_2$|file|
|-|-|-|-|-|
|$(12,12,6)$|$206$|$271$|$65$|`spreadcompat_663.json`|
|$(16,16,8)$|$994$|$1251$|$257$|`spreadcompat_884.json`|
|$(20,20,10)$|$2658$|$3683$|$1025$|`spreadcompat_10105.json`|

The three counts were obtained by ILP over the corresponding pool, stopped at a
time limit, and are therefore lower bounds on the maximum available in each
pool -- which is all the construction requires. Each file lists the
spread-compatible codewords themselves.

`build_lift.py` turns a spread-compatible base into the lifted family and
verifies it at the new parameters from first principles: it rebuilds the
Desarguesian spread of $\mathbb{F}_2^{2n}$, forms the diagonal lifts
$D_i=\iota(C_i\times C_i)$, and checks that every codeword of the resulting
family is a nondegenerate subgroup of order $2^{2k}$, that all pairs meet only
in the identity, and that each $D_i$ is itself spread-compatible in $U_{2n}$ --
the last being what the tower corollary of the paper needs in order to iterate.

```
python code/build_lift.py --base cliques/spreadcompat_663.json  --n 6  --k 3
python code/build_lift.py --base cliques/spreadcompat_884.json  --n 8  --k 4
python code/build_lift.py --base cliques/spreadcompat_10105.json --n 10 --k 5
```

Only the smallest lifted family, `clique_12126_lift.json`, is included here: the
$(16,16,8)$ family is around $40$ MB and the $(20,20,10)$ family around
$500$ MB, since a codeword of order $2^{2k}$ lists $2^{2k}$ elements. Both are
regenerated deterministically by the commands above and can then be checked with
`verify_psc.py` in the usual way. Each run also writes a small
`results_<ndk>_lift.json` recording $m$, the spread size and the number of pairs
verified; the `_lift` suffix keeps these files apart from the computed cliques,
since lifting the $(4,4,2)$ base would otherwise land on `clique_884.json`.

We avoid the term *fixed-point-free* for this condition: in the literature on
propelinear codes it denotes the stronger requirement that each permutation
move every coordinate, which defines the full propelinear codes and is not what
the lift needs.

## Requirements

Python 3.9 or later and PuLP, which ships the CBC solver:

```
pip install -r requirements.txt
```

Nothing else is needed; the scripts use only the standard library beyond PuLP.
Only `psc_gen.py`, `ilp_subpool.py`, `exact_k2.py` and `spreadcompat_max.py`
import PuLP; `verify_psc.py`, `build_lift.py` and `structural_stats.py` run on a
bare Python installation, so checking the deposited cliques needs no
dependencies at all.
